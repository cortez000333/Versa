# Versa — Project Status

## Strategic direction (pivot — June 2026)
**The model has changed.** Versa is moving *away* from being a manually-maintained scorecard database — keeping a full market database current is too much data burden for a solo founder. The new shape has three pillars:

1. **User-fed tools = the scalable core.** The user brings their own data; Versa does the math and the framing. No DB to maintain.
   - **True-yield calculator** — *done* (`components/TrueYieldCalculator.tsx`).
   - **Portfolio tracker** — *in build* (Pass 1 done; Pass 2 persistence foundation done; spec below).
   - **Alerts** — later.
2. **Paid research-on-demand = the money.** This monetizes Alessandro's *judgment*, not a database: bespoke due-diligence reports on a specific asset, sold one at a time. **Framed as research, not advice** (no recommendations, no "buy/sell").
3. **Scorecard showcase = credibility, not coverage.** Keep only a small, hand-curated **3–5 asset** public scorecard set as proof of rigor. This is a showcase, *not* a market database to keep complete.

**Scope guardrail:** focus on **institutional, API-covered assets** (Ondo, Circle, BlackRock, etc.) — things with reliable public data, so the tools stay accurate without manual upkeep.

**Decided AGAINST (and why — don't revive these):**
- *AI-generated scores* — destroys the moat (the human judgment is the product) and carries hallucination risk.
- *Live yield feeds* — would require the pricier RWA.xyz API; not worth it yet.
- *A screener as originally conceived* — secretly depends on a maintained DB, which is exactly the burden we're escaping.

**Decided FOR (June 18) — user accounts for the tracker:** the tracker was conceived session-only / user-fed / no-DB. We've now *added* an opt-in dimension: logged-in public users can save and reload portfolios. This is deliberate, not scope-creep — the session-only flow stays the default; saving is opt-in for signed-in users. It does NOT revive the "maintained market database" burden (users save their *own* data; Versa maintains nothing).

### Portfolio tracker — build spec
**One live input only:** current price / NAV via **CoinGecko free tier**. Everything else is static / user-entered: amount, price paid, headline yield, fees (flat / performance / entry / exit), redemption & settlement terms, asset class, chain, issuer.

**Outputs — all deterministic, no advice, just facts and math:**
- Total invested + current value
- Blended true yield (across the whole portfolio)
- Total real cost / fee drag
- Estimated annual income
- Headline-vs-true-yield gap
- Composition breakdown (concentration stated as a *neutral fact*, not a warning)
- Per-position true yield
- Redemption / liquidity profile
- *Possible additions:* yield-on-cost, cost-to-exit-everything

**Build in passes (renumbered June 18 to avoid collision):**
1. **Pass 1 — calculation engine + UI** (running entirely on user-entered numbers). **DONE.**
2. **Pass 2 — PERSISTENCE** (save/load portfolios for logged-in public users via Supabase Auth). **Foundation done; UI pending.**
3. **Pass 3 — LIVE PRICE** (wire in the live CoinGecko free-tier price, replacing the user-entered `currentPrice`). **Not started.** (This was the original "Pass 2"; renumbered.)

Reuse the true-yield math already in `TrueYieldCalculator.tsx` where possible.

Positions live in React state only; a refresh clears them (expected, in the session-only default flow).

Every division is guarded so empty/zero inputs return `null` → "—", never NaN.
  - **UI** (`components/PortfolioTracker.tsx`, client) mirrors the calculator's conventions exactly (same brand-token constants, inline styling, `<Stat>` subcomponent). Outputs are deterministic facts, **no advice**.
  - **Horizon rule:** only a *valid future* maturity date drives the holding horizon; otherwise the "Intended holding period (yrs)" number (default 1) is used. A today/past/blank maturity is ignored — this was the fix for an earlier "true yield = −296.5%" bug (a today maturity had collapsed the horizon to a 0.01yr floor, ~100×-ing every fee-drag term).

Text fields start blank; a small `isValidYmd()` validates the format (invalid text is cleared on blur), and blank/invalid saves as `null`.

  - **RLS is the entire security boundary.** Four policies (`portfolios_select_own`, `_insert_own`, `_update_own`, `_delete_own`), all keyed `auth.uid() = user_id`; insert + update use `WITH CHECK` (update has both `USING` and `WITH CHECK` so a user can't reassign ownership). RLS is ONLY enforced through the publishable/anon key carrying a user's JWT — the secret-key `supabaseAdmin` client BYPASSES RLS, so portfolio reads/writes must use the public `supabase` client, never `supabaseAdmin`.
  - **The two Supabase clients now live in SEPARATE files** (split June 23, Chunk A): `lib/supabase.ts` contains ONLY `supabaseAdmin` (secret key, server-only, RLS-bypassing — unchanged); a NEW file `lib/supabaseClient.ts` contains ONLY the public `supabase` client (anon/publishable key, RLS-respecting, browser-safe — for public auth + portfolio save/load). **Why the split:** the `/account` page is a client component, and importing the public `supabase` from the old *combined* file dragged `supabaseAdmin` into the browser bundle, where the server-only `SUPABASE_URL` (no `NEXT_PUBLIC_` prefix) is undefined → runtime crash `"supabaseUrl is required"`. **Rule going forward:** browser/client code imports the public client from `lib/supabaseClient.ts`; server code imports `supabaseAdmin` from `lib/supabase.ts`.
  - **BUG FIXED — dual-client / JWT race (June 23).** `lib/supabaseClient.ts` now caches a **single shared browser client on `globalThis`**, created with explicit auth options `persistSession` / `autoRefreshToken` / `detectSessionInUrl`. Symptom: portfolio reads/writes intermittently went out **unauthenticated** (no `Authorization: Bearer <jwt>`). Cause: React Fast Refresh / repeated module evaluation spun up **duplicate `GoTrueClient` instances** sharing the same storage key, which raced over the stored session — the loser made DB calls without the logged-in user's JWT. One shared instance means the session established at `/account` login is the exact session the tracker's queries authenticate with, so every request carries the JWT.

  - **BUG FIXED — missing table GRANT (migration `007_grant_portfolios_authenticated.sql`, June 23).** Migration 006 created `portfolios` with RLS policies but **no base table privileges** for the `authenticated` role. Postgres checks table-level GRANTs **before** RLS, so every logged-in read/write failed with `permission denied for table portfolios` (code **42501**) — RLS never even ran. Fixed by `GRANT SELECT, INSERT, UPDATE, DELETE ON portfolios TO authenticated` (`anon` intentionally NOT granted — only logged-in users save). **House rule for future tables:** a new RLS-protected table needs BOTH the policies AND a GRANT to `authenticated`, or every request 403s before RLS runs.
